## 2. 4장 고친 문장 (그대로 붙여 넣기용)

### 4.1 Fogify 테스트베드

- **구성:** PC 1대(i5-1240P), Docker Swarm. 로컬 1대(**0.2 CPU**)와 엣지 서버 2대(각 2.0 CPU)이다.
  - 로컬 CPU를 0.2로 정한 이유: 엣지 서버가 로컬보다 약 5배 빠르게 만들어, 스마트폰·IoT 기기와 서버의 실제 계산 능력 차이(약 3~10배)를 반영했다.
  - Fogify는 CPU 할당을 소수 첫째 자리로 반올림하므로 0.2가 5배에 가장 가깝다.
- **수정 사항:** cgroup v2 호환(cAdvisor, 모니터링 경로)과 대역폭 단위 오류(Mbps가 실제로는 MB/s라서 Mbit 사용)를 고쳤다.
- **격리:** 엣지 서버마다 E코어 묶음을 분리했다 (엣지 서버 1: 코어 8·9, 엣지 서버 2: 12·13, 로컬: 14).
  - 격리 전에는 엣지 서버 1에 부하를 걸면 엣지 서버 2가 27.4% 느려졌다.
  - 격리 후 엣지 서버 2의 변화는 −0.3%이다.
- **CPU 고정:** CPU 거버너를 performance로 두고 E코어의 깊은 절전 상태(C6 이상)를 껐다.
  - 고정 전에는 같은 작업의 엣지 서버 연산 시간이 쉬는 시간과 측정 구간에 따라 67.7~90 ms로 흔들렸다.
  - 고정 후에는 72.1 ± 0.4 ms이다.
- **채택 이유:** 실제 코드와 네트워크 스택을 실행하는 에뮬레이션이라 시뮬레이션보다 현실과의 차이가 작다(5~15% vs 15~40%) [2]. RTT, 대역폭, 부하를 실행 중에 바꿀 수 있다.

### 4.2 워크로드

- SHA-256 반복 해시이다. iter로 연산량을 조절하며, 기본값 1M은 엣지 서버 연산 **72.1 ms**에 해당한다. payload는 1KB / 256KB이다.
- 출처: Unikernels vs. Containers 논문의 공개 코드.
- 로컬과 엣지 서버가 같은 해시 함수를 써서 연산량이 정확히 같다.

### 4.3 변수 조작과 측정 → `<Table 3>`

- **대역폭:** `tc` rate 1 / 10 / 100 Mbit (실측이 이론값과 일치).
- **엣지 서버 CPU 부하:** stress 0~90% (`cpulimit -i -- stress`). cAdvisor로 관측한 부하는 60~90% 설정에서 ±0.06 안이고, 30% 설정에서는 0.45로 가장 크게 벗어났다.
- **작업 도착:** closed-loop. 앞 작업이 끝나고 평균 200 ms(지수분포) 쉰 뒤 다음 작업이 생긴다.
- **측정:**
  - 작업별 TCT, p50·p95, 조건당 n = 30.
  - 정책들을 10개씩 3라운드로 섞어 실행했다.
  - 사후 최적 대비 손해(ms)로 비교한다.
- **사후 최적:** 같은 작업 순서로 따로 실행한 Always-Local / Edge1 / Edge2 결과에서 작업마다 최솟값을 골랐다.

### 4.4 RQ1 → C1: 손익분기 `(Fig. 2)` `(Fig. 3)`

- **로컬 TCT는 일정하지 않다.**
  - CPU 할당량(CFS) 때문에 작업 사이 쉬는 간격에 따라 230~390 ms로 바뀐다. 연속 실행하면 310 / 390 ms 두 갈래로 나뉜다.
  - 테스트베드에 맞춘 CFS 모델이 이를 재현한다.
- **수식 모델의 첫 번째 오류: 로컬을 상수(350 ms)로 본다.**
  - 그래서 빨리 끝나는 로컬 작업을 놓친다.
  - RTT 205 ms에서 사후 최적은 작업의 30%(1KB)~60%(256KB)를 로컬로 골랐다. 수식 기반 Model-Greedy는 0%였다.
- **(Fig. 2) TCT vs RTT**
  - 1KB는 RTT 약 200 ms까지 엣지 서버가 낫다. 수식과 실측이 맞는다.
  - **256KB는 실측 손익분기가 RTT 약 105 ms로, 수식(크기 ÷ 대역폭)이 예측한 약 200 ms의 절반이다.**
- **수식 모델의 두 번째 오류: TCP slow start를 모른다.**
  - 리눅스 기본값(`tcp_slow_start_after_idle = 1`)에서는 작업 사이에 쉬는 동안 TCP 혼잡 윈도우가 초기값으로 돌아간다. 그래서 256KB를 보내려면 RTT를 1~4번 더 왕복한다 (RTT 205에서 p50 493, p95 1103 ms, 수식 298 ms).
  - 이 설정을 끄고 다시 재면 엣지 서버 TCT가 수식과 1~3 ms 안으로 맞고, 손익분기도 약 200 ms로 돌아온다.
- **(Fig. 3) TCT vs 대역폭**
  - 1KB는 1 Mbit에서도 엣지 서버가 낫다.
  - 256KB는 10 Mbit에서 로컬과 엣지 서버가 비슷하고(308 vs 300 ms), 1 Mbit에서는 로컬이 낫다(296 vs 2262 ms).
- **결론:** 수식 모델은 로컬 실행 시간의 변동과 전송 계층의 동작을 반영하지 못해, 큰 작업에서 엣지 서버를 과대평가한다. 실제 손익분기는 작업 간격과 TCP 설정에 따라 달라진다.

### 4.5 RQ2 → C2: 엣지 서버 간 역전 `(Fig. 4)`

- **조건:** 엣지 서버 1은 RTT 10 ms에 부하 0~90%, 엣지 서버 2는 RTT 50 ms에 부하 0이다.
- **(Fig. 4)**
  - 1KB에서 엣지 서버 1은 부하 0 → 90%에서 83 → 140 ms로 느려진다. 엣지 서버 2는 123 ms로 일정하다.
  - **역전 부하는 실측 약 72%**이고, 부하에 따른 속도 모델(1 − 0.526·L)의 예측은 68%이다.
  - 256KB는 slow start를 끈 상태에서 약 70%에서 역전된다. 켠 상태에서는 먼 엣지 서버 2의 slow start 비용이 커서 0~80% 안에서 역전되지 않는다.
- **네트워크만 보는 정책 vs 상태도 보는 정책 (부하 90%, 1KB)**
  - Nearest-Edge(RTT만 봄)의 손해는 **27.1 ms**이다.
  - 부하를 함께 보는 Model-Greedy는 3.0, QECO-net+는 3.1, QECO-net은 3.6 ms이다.
  - 실행 중 조건이 바뀌는 S4의 부하 80% 구간에서도 Nearest-Edge 25.1 ms vs QECO-net+ 2.6 ms였다.
- **결론:** 역전점을 넘으면 가장 가까운 엣지 서버가 정답이 아니다. 네트워크만 보는 정책은 크게 손해 보므로 서버 부하도 함께 봐야 한다.

### 4.6 RQ3 → C3: 시뮬레이터 학습 정책의 실측 검증 `<Table 4>`

- **불일치** (open-loop로 학습, closed-loop로 평가)
  - 1KB S1~S3 손해는 7.5 ms, S4는 8.3 ms이다.
  - Phase 4에서는 학습 시뮬레이터의 로컬 큐 정보에 기대 "항상 로컬"을 골랐다.
- **일치** (closed-loop로 다시 학습): QECO-net의 손해는 **2.7 ms** (S4 2.6 ms)이다.
- **상태 보강** (QECO-net+, 로컬 CPU 상태 추가): **2.1 ms** (S4 **1.9 ms**, 전체 정책 중 가장 작음)이다.
  - 조건을 맞춘 효과(7.5 → 2.7)가 상태를 보강한 효과(2.7 → 2.1)보다 크다.
- **QECO-orig** (원본 상태만, 네트워크·부하를 보지 않음)
  - 학습 조건을 맞춰도 "작업 크기만 보는 고정 규칙"이 된다.
  - 1KB 손해 7.5 ms, S4 손해 38.2 ms이다. RTT가 205 ms로 바뀐 엣지 서버를 계속 골랐기 때문이다.
- **규칙 기반과 비교**
  - 1KB에서 Model-Greedy는 1.6 ms로 학습 정책과 비슷하다. 시뮬레이터와 수식이 정확한 영역이기 때문이다.
  - 조건이 실행 중 바뀌는 S4에서는 QECO-net+ 1.9 ms가 Model-Greedy 2.6, Nearest-Edge 6.3 ms보다 작다.
- **시뮬레이터 성적 vs Fogify 성적** (같은 정책·조건의 평균 TCT 차이)
  - 1KB에서는 1~2 ms로 맞는다.
  - 256KB에서는 QECO-net이 53.6 ms(RTT ≥ 55에서 141.7 ms) 차이가 났다. 시뮬레이터가 slow start를 모르기 때문이다.
  - slow start를 끄면 4.0 ms로 줄어든다.
- `<Table 4>`: 정책별 TCT p50·p95와 사후 최적 대비 손해(조건별)를 넣는다.
  - 시뮬레이터는 시드 3개의 평균 ± 표준편차이다.
  - Fogify는 검증 성능 기준으로 고른 시드 1개이다.

## 3. 다른 장에서 함께 고칠 곳

### 초록 주요 결과 (예시)

> Fogify 기반 에뮬레이션 테스트베드에서 RTT, 대역폭, 엣지 서버 부하를 바꿔 가며 작업 완료 시간(TCT)을 실측했다.
> 256KB 작업의 실측 손익분기 RTT는 약 105 ms로, 전송 시간을 크기 ÷ 대역폭으로 보는 기존 수식의 예측(약 200 ms)의 절반이었다. 원인은 TCP slow start였다.
> 가까운 엣지 서버가 먼 엣지 서버보다 느려지는 부하는 약 72%였고, 이를 넘으면 RTT만 보는 정책은 27 ms 손해를 봤다.
> 시뮬레이터로 학습한 QECO는 학습·평가 조건이 다르면 손해가 약 3배였다. 조건을 맞추고 로컬 CPU 상태를 더한 QECO-net+는 동적 환경에서 사후 최적 대비 1.9 ms로 가장 작은 손해를 보였다.

### 1.4 기여 (RQ와 1:1)

- **C1 (RQ1):** 상태를 바꿔 가며 로컬과 엣지 서버의 손익분기를 실측했다. 기존 수식 모델이 로컬 실행 시간의 변동과 TCP slow start를 반영하지 못해, 큰 작업에서 손익분기를 약 2배로 잘못 잡는다는 것을 보였다.
- **C2 (RQ2):** 가깝지만 바쁜 엣지 서버와 멀지만 한가한 엣지 서버의 역전 지점(약 72%)을 실측했다. 네트워크만 보는 정책이 역전점 이후 크게 손해 본다는 것(27 ms vs 3 ms)을 보였다.
- **C3 (RQ3):** 시뮬레이터로 학습한 QECO를 실측 환경에서 검증했다. 학습·평가 조건 불일치와 상태 설계가 성능을 좌우한다는 것(7.5 → 2.7 → 2.1 ms)을 보였다.

### 3.3 TCT 모델

- T_local = C / 로컬 CPU 속도라고 쓴 뒤, **실제로는 CPU 할당량(CFS) 때문에 230~390 ms로 변동한다**고 각주로 단다.
- T_edge,i = T_comp,i(C, L_i) + R_i + D/B_i는 **slow start가 없다고 가정한 식**이라고 명시한다. 이 가정이 4.4에서 깨진다.
- T_comp(C, L) = T_comp(C, 0) / (1 − α·L), α = 0.526 (실측 맞춤).

### 3.4 비교 정책

- QECO-net+의 추가 상태: 직전 로컬 작업이 끝난 뒤 지난 시간과 그 작업의 TCT.
  - 드라이버가 직접 아는 값이다.
  - cgroup `cpu.stat`에는 누적값만 있어서 현재 주기의 남은 할당량은 읽을 수 없다.

### 5.2 한계 (추가)

- **TCP slow start:** 시뮬레이터가 이를 모델링하지 않는다. 끄면 맞는다는 것은 확인했으며, 기본 설정에서도 맞히는 전송 모델은 후속 과제이다.
- **평가 시드:** Fogify 평가는 QECO 시드 1개(검증 기준 선택)로 했다.
- **워크로드:** SHA-256 한 종류이다. ML 추론은 하지 않았다.
- 그 밖에 기존 항목: 단일 PC 에뮬레이션, 사용자 1명(다른 사용자는 엣지 서버 CPU 부하로 대체), 에너지 미측정.

### RQ1 "얻은 것" 문단 (교체용)

- **얻은 것:**
  - 수식은 로컬 시간을 한 값(350 ms)으로 보지만, 실제로는 CPU 할당량 때문에 230~390 ms로 들쭉날쭉하다. 그래서 빨리 끝나는 로컬 작업을 놓친다.
  - 큰 작업에서는 TCP slow start 때문에 엣지 서버가 수식보다 최대 2배 느려서, **수식이 경계를 약 2배로 잘못 잡는다.**
  - 수식으로 판단하면 틀린다는 첫 증거이다.
